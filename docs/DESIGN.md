# Design

`bigsister` reads the transcripts that coding agents write on your machine and reports where tokens and checks are wasted. The [README](../README.md) lists the agents, each subcommand and the agents it reads, its options and, under [Privacy](../README.md#privacy), what the output holds. This file defines how each input is read and each measure taken.

## Detectors

`bigsister all` runs every detector in one pass over the files.

Coverage limits: `schemas` gives a tool only ever sent with `defer_loading` no row, as its schema enters context through ToolSearch results, which are not measured. `pipes` judges local commands only; commands sent over `ssh` are counted but not judged, because the remote shell's settings are unknown. Test runners inside shell functions or `bash -c` scripts are not recognised. Codex can run PowerShell, where a pipe does not hide a native command's exit status in the same way. A Codex `exec` call can run several commands and returns one output: a list of text items or one string. In its texts that are JSON, the objects with an `exit_code` and an `output` are command results, whether a text is one, as `text(await tools.exec_command(...))` prints it, or holds them in lists and objects, as a printed `Promise.allSettled` does (`{"status": "fulfilled", "value": {...}}`); a null `output` is an empty one. Results keep the order printed; an object that holds results under more than one key gives the call none, as its keys' order is not kept, and so do entries numbered by an `i` (`{"i": 0, "status": ...}`) whose numbers, among those holding results, do not rise in the order printed. A result still running, which has a `session_id` and no `exit_code`, is not one, and it too gives the call none, as a result printed after it may be another session's, such as one `write_stdin` gave; nor is text printed from part of a result a result. Each command is first tied to the item Codex recorded as it ended (Codex results, below). A command no item ties pairs with the printed result at its position only when the call printed one result per command and has one command, Codex recorded no item whilst the call was open, or every tied command's printed result is at its own position. `polls` and `pipes` report a call with a command left unpaired under `codex_outputs_not_paired` (`pipes` counts only calls with an unguarded test run, and `polls` also counts those commands under `codex_commands_not_paired`), as they do a call in the window that has no call id, whose output never comes before the file ends, or whose id another `exec` call in the session also carries, in which case neither call pairs. A non-zero exit code marks a failure. A result's size, for `polls`, is the characters the cell printed of its output. For `rereads`, a Codex result is all the text the call's output holds, and `codex_outputs_not_paired` counts the calls that re-read but have no call id, share it with another `exec` call or have no output. The outputs of `function_call` records are not read, so `pipes`, `polls` and `rereads` count a `function_call` whose result they would have read under `codex_outputs_not_paired`, and `polls` counts its command under `codex_commands_not_paired`.

## Inputs

- Claude Code: `~/.claude/projects/**/*.jsonl`. A file under a `subagents` folder is a subagent session. Records used: `assistant` (`tool_use` blocks), `user` (`tool_result` blocks), `attachment` (instruction files, hooks, listings, deltas), `system` with subtype `compact_boundary`, `api-request-shape` (the system prompt and tool definitions sent with a request; a tool with `defer_loading: true` is not loaded into context), and for `context` the rest of the request log: `api-request` (a request: its shape, the request it extends and the messages it adds) and `api-request-blob` (a message as sent, where the transcript does not hold it so). Request blobs are passed to no other detector. With `context` chosen, a request blob line that is cut short or cannot be parsed counts in `lines_skipped`, as any line a chosen detector reads does; otherwise blob lines are neither read nor counted.
- Codex: `~/.codex/sessions/**/*.jsonl` and `~/.codex/archived_sessions/**/*.jsonl`, where Codex moves older sessions. Compressed `*.jsonl.zst` transcripts in either folder are decoded as they are read; one that does not start with the zstd magic number counts as a compressed file skipped, and one whose frame header cannot be read (including a window over 128 MiB), that fails part way, fails its checksum or holds more than one frame counts as unreadable. The first record, `session_meta`, marks a subagent session by its `parent_thread_id`. Records used: `custom_tool_call` named `exec` and its `custom_tool_call_output`, whose input is code calling `tools.exec_command({cmd: ...})`, `readFile(...)` or `readFileSync(...)`, and the edits `apply_patch(...)`, `writeFile(...)` or `writeFileSync(...)`, taken in source order, skipping the text of patch bodies (from a string that opens with `*** Begin Patch` to `*** End Patch`, unless the quote follows `//` on its line other than in `://`), which is written, not run; `function_call` named `apply_patch` (an edit) or with a `cmd` or `command` argument; and `compacted`. A `cmd` or read path in a cell counts only when its value is one string literal. One the cell builds from other values, with `+`, a method or a `${}` substitution in a template literal, is not read, so different commands built from the same text are never taken for repeats.
- pi: `~/.pi/agent/sessions/**/*.jsonl`, in the format pi's `docs/session-format.md` documents (read 16 November 2026, pi 1.5.2). Each entry is rewritten into the Claude Code record the detectors read (`src/pi.rs`): an `assistant` message into an `assistant` record with its model first and its `usage` under Claude's names; its `toolCall` blocks into `tool_use` blocks, with `bash` and `powershell` as `Bash`, `read` as `Read` (`path` as `file_path`), and `edit` and `write` as `Edit` and `Write` (`path` as `file_path`, keeping other fields); a `toolResult` message into a `user` record with one `tool_result` (`isError` as `is_error`); and a `compaction` into a `compact_boundary`. Every other entry becomes a record holding only its time, so the detectors ignore it whatever its fields. An entry's id and timestamp together act as Claude's `uuid`, as a fork (`/fork`, or `/tree` into a new file) copies entries with both; in a session whose header names a `parentSession`, an entry that file holds (matched by file name, so a moved folder still matches; its entries include those it copied in turn) is a copy and counts once, and files are read in order of their first timestamp. A fork names only its own parent, so when that file is not read (deleted, or outside the roots scanned), the entries it copied from its own parent count again in the fork. An entry whose id an earlier entry in its file carries leaves unknown which of the 2 later entries continue from, so it and every entry continuing from that id are skipped and counted as skipped lines. A session's branches share one file: when an entry continues from an earlier entry than the last one read, the detectors drop the state of the path left behind and are given the path from the root to that entry again, as copies that build state and count nowhere, so each command and read is judged against its own path; counts already made on the path left behind stand. pi has no subagent files. `pipes`, `polls` and `rereads` read pi; `startup`, `schemas` and `hooks` do not.
- Gemini CLI and Qwen Code: `~/.gemini/tmp/**/*.jsonl` (sessions in `<project>/chats/session-<time>-<id>.jsonl`) and `~/.qwen/projects/**/*.jsonl` (`<folder>/chats/<session id>.jsonl`), in the formats Gemini CLI 0.69.0 and Qwen Code 0.28.0 wrote on 19 November 2026, run headless against a local stub endpoint with a dummy key; neither documents its format. Each line is rewritten into Claude Code records (`src/gemini.rs`), under the scan's line limit. Gemini CLI writes a reply again under the same `id` as its tool calls progress, so the last record of the same `type` and `id` stands for it, in its own place: a Gemini CLI file is read twice, first for the line of each record's last version, so memory holds one line and a type and id for each record; a `gemini` record becomes an `assistant` record, its `toolCalls` `tool_use` blocks, and each call with a `result` a `user` record with one `tool_result` (`status` `error` or `cancelled` as `is_error`, the `functionResponse`'s `output` or `error` as content). In Qwen Code's files an `assistant` record's `functionCall` parts become `tool_use` blocks and a `tool_result` record's `functionResponse` parts `tool_result` blocks (`toolCallResult.status` `error` or `cancelled` as `is_error`). A Gemini CLI line with no `id` that is not the header or a `$set`, `$patch` or `$rewindTo` record, a call without a non-empty string `id` and name, a result without a non-empty string `id`, a Gemini CLI result part without a `functionResponse` (a call whose result holds only such parts gets no result), and a `toolCalls`, `result` or `parts` field that is not a list each count as one skipped line; a byte that is not UTF-8 spoils only the text it is in. Both name `run_shell_command` as `Bash`, `read_file` as `Read`, `replace` and `edit` as `Edit` and `write_file` as `Write`, whose arguments already use Claude Code's names, and give usage under Claude's names, a prompt's cached tokens taken out of its prompt tokens. Records without a tool call, result or compaction retain their time. Other versions are unverified, and Gemini CLI's older `session-*.json` files are not read. Qwen Code `system` records with subtype `chat_compression` and a `systemPayload.compressedHistory` array become compaction boundaries for `rereads`. The parser keeps the record's time and ID and discards the replacement history. Gemini CLI's compaction records, its subagent header and Qwen Code's parent session record are unread, so each session counts as a main session.
- OpenCode: `~/.local/share/opencode/opencode.db`, the SQLite database OpenCode 1.18 and later keep sessions in, in the schema of its `packages/schema/src/v1/session.ts` (read 16 November 2026, v1.19.5; this machine's database was written by 1.18.23). The file is copied into memory with ordinary reads, sharing it fully, and read twice. No lock is taken, so another program, OpenCode included, opens, writes and checkpoints as it would were `bigsister` not running. The copy counts only if both reads match, the file's size and time, the lengths of the write-ahead log (`-wal`) and the rollback journal (`-journal`) and whether the log's index (`-shm`) exists are unchanged, and SQLite's `quick_check` passes on the copy, so it is the file as it stood, not pages from before and after a write. These checks detect a write rather than prevent one. For OpenCode's database, which uses the log, a copy holding pages from 2 states passes them only if a checkpoint rewrites pages in place, stalls across both reads and empties or removes the log before the second stamp without moving the file's time: within the file clock's resolution, or on Windows, which need not move the time whilst a writer holds the file open. OpenCode asks only for `PASSIVE` checkpoints and sets no `journal_size_limit` (its `packages/core/src/database/database.ts`, read 17 November 2026 at v1.19.6), and SQLite's automatic checkpoints do not shrink the log without that limit (SQLite's write-ahead logging page), so the one checkpoint that does this is SQLite's last when OpenCode closes the database cleanly, which then deletes the log. A writer with no journal on disk (`journal_mode` `OFF` or `MEMORY`) that stalls across both reads passes them too. The bundled SQLite (`rusqlite`) opens the copy read-only, and only `session`, `message` and `part` are queried, with fixed SQL; the database also holds account tokens and credentials, so an SQLite authoriser refuses a read of any other table. No file beside the database is opened, written, created or deleted. SQLite's own read-only connection is not used for that reason: even with `mode=ro` and `readonly_shm=1`, SQLite 3.54.1 creates the log when it is missing, and on Windows the index too. OpenCode's newest records sit in the log, which only a connection sharing the index can read: so committed records still in the log are not read, and a log holding records counts as an unreadable file. From OpenCode's first write after it starts until its log is emptied, as on a clean stop, the log holds records, so its sessions are read only then, and after OpenCode is killed only once it has next started and stopped cleanly. A journal holding records, from a write under way or cut short, counts as an unreadable file too. The report prints the reason an OpenCode database is unreadable beside the root's counts, as for any unreadable file, with what to do where the user can act; it holds no table content, and an error other than SQLite's own message is named only as such. A database that cannot be read, whose presence cannot be checked, or that lacks those tables, counts as one unreadable file and none of its sessions count. A message or part whose data is not a JSON object, or a tool part without its state, counts as a skipped line. Each session updated in the window counts as one file, read as one transcript (`src/opencode.rs`): an assistant message holds one or more steps, each a model call from a `step-start` part to a `step-finish` part, and each step becomes a Claude `assistant` record (the message's `modelID` first, the step's token usage under Claude's names) holding a `tool_use` block for each `tool` part of the step, followed by a `user` record holding the `tool_result` of each call that finished (`output` when completed, `error` marked as an error, and an `image` block for each attached file of an `image/` type and a `document` block for each other, without its address); a pending or running call has no result. A step whose `step-finish` is missing ends at the next `step-start`. `bash` is named `Bash`, `read` `Read` (`filePath` as `file_path`, the other input fields kept), and `edit` and `write` `Edit` and `Write`. A `compaction` part becomes a `compact_boundary`. A result's size is the output OpenCode stored for the call; how it truncates long output, and its later pruning of old outputs from the context, are not measured. A session with a `parent_id` counts in the subagent scope. `pipes`, `polls`, `rereads` and `tools` read OpenCode; `startup`, `schemas` and `hooks` do not.

Claude Code's and Codex's formats are undocumented and change between releases. `bigsister` skips a line that is cut short (does not end in `}`), that is longer than 64 MiB (left unread, since a small compressed file can decode to a line of any length) or that a detector needs but cannot parse, and reports how many it skipped; it counts unreadable files and folders and never fails a run because of one. Each distinct reason prints under its root's counts, with how many files or folders it covers when more than one (`unreadable_reasons` in JSON: `reason` and `count`, an empty list when none): a folder that cannot be listed or whose entry cannot be read, or a file whose time cannot be read or that cannot be opened or read, each with the system's message, or a `*.jsonl.zst` one whose frame header cannot be read or whose data cannot be decoded, named only as such, since a decoder's message can quote the data. A reason names no file, so no project folder prints. A file is read only if it was modified at or after `--since`; within it, a record counts only if its own timestamp is at or after `--since`. A record without a timestamp takes the last one seen in its file. A Claude record whose `uuid` an earlier record in its file carries is a copy that Claude Code wrote again, and is skipped. One whose `uuid` a record in a file read earlier carries, as when a resumed session's file starts with the earlier session's records, or an `assistant` record whose `message.id` an `assistant` record in a file read earlier carries, under any `uuid` (Claude Code 2.1.308 wrote a block of a subagent's reply again in sibling subagent files under new uuids), builds its session's state but counts as outside the window, so it is counted once, and adds nothing to `startup` once its session has started in the window. Claude files are read in order of their first record's timestamp, then path, so an original is read before a copy of part of it, whose first record is later; read the other way, the copy would count records whose earlier context it lacks. A record without a `uuid`, such as `api-request-shape`, counts in each file that holds it. Only the roots of agents that a chosen detector reads are scanned and listed. Session state, such as which files were read before a compaction, is built from the whole file, so a re-read early in the window is still recognised. A file is read only as far as some chosen detector still needs it: `startup` alone stops at a main session's first reply, so lines after it are neither read nor counted as skipped.

## Measures

- Sizes are characters (Unicode scalar values) of the text as stored, or of compact JSON for structured values. A tool result's size is the characters of its text: a string, or the text blocks of a list. A block without text, such as an image, adds nothing.
- A Claude result pairs with the `tool_use` block whose id it carries. Once a second block in the session carries the id, no later result with it pairs with either block in `pipes`, `polls` or `rereads`, as the results cannot be told apart.
- Tokens come from the transcript only where Claude Code records them: a first request's tokens are the `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` of the session's first reply. `sessions_with_request_tokens` counts the measured sessions whose first reply records them as non-negative integers, and whose sum fits in 64 bits; a missing or null cache field counts as 0. A reply with model `<synthetic>`, which Claude Code writes itself, such as an error notice, follows no request, so it is not a first reply: `startup` reads on to the next reply, and a session with no other reply is not measured. Columns ending in `_tokens_est` are estimates, the characters beside them divided by 4 and rounded up in each row, so rows need not add up to a total; the model's own tokenizer, which is not published, gives a different count. A `_usd_est` column follows each, printed with 2 decimals in text and as a number in JSON, then `unpriced_tokens_est`. Dollars are each character count divided by 4, times the uncached input price per million tokens of the model that read it, summed over the row and rounded to cents once. The prices are a table bundled from `src/prices.json`, read on 16 November 2026, keyed by the exact model id a transcript records; an id it lacks is unpriced. `--prices FILE` replaces the table with a price file in the same format (LiteLLM's field names: `input_cost_per_token` in US dollars a token, and `input_cost_per_token_above_<N>k_tokens` for a prompt over N thousand tokens, the highest such N below the prompt applying), and each priced section's note names the file. A malformed file stops the run before any transcript is read. Claude Haiku 5.5's price depends on the prompt's size, so its reply is parsed for its `usage`: a prompt of `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` up to 100,000 tokens takes the lower price, a larger one the higher, counted as `startup` counts a first request; a reply whose count is unknown leaves what it read unpriced. The reader is the next Claude reply in the file (a synthetic reply, or a reply's record written again with its uuid, reads nothing; a result no reply follows is unpriced), the model of the Codex `turn_context` the result came in (none before the first), at the prompt size of the first `token_usage_record` after the result in that turn (its `usage.input_tokens`; Codex writes one as each model call completes, so the call it records read the results before it; a result no record follows in its turn has no known prompt size). A tool can finish whilst the call that asked for it is still writing, so its result comes before that call's own record and is priced at that call's prompt, which lacks it (6 of 92,410 results in 895 real rollouts in November 2026, each within 3,000 tokens of the next call's prompt and on the same side of 272,000). GPT-6 and GPT-5.6 models take OpenAI's long-context price for a prompt over 272,000 tokens; one whose prompt size is unknown leaves what it read unpriced, and for `schemas`' idle characters the session's replies, when all their models have one price (otherwise they are unpriced). `unpriced_tokens_est` is the row's estimate less the estimate of its priced characters. With `--usd-per-mtok USD`, every `_usd_est` is the estimate times USD over 1,000,000 instead (for `cache`, times the write multiplier too), and nothing is unpriced. Either way an estimate is priced once as uncached input; no cache rate or later turn is reconstructed. The bundled table goes out of date as models are released or repriced; it trades that for making no network call, and a price file keeps prices current without one. `startup`'s request tokens are measured and include cache reads, so they stay unpriced.
- Commands are split into simple commands at unquoted `|`, `|&`, `||`, `;`, `&`, `&&` and newlines. `#` comments, heredoc bodies (also when written `cat<<EOF`) and PowerShell here-string bodies (from `@'` or `@"` to `'@` or `"@`) are skipped. Backslash escapes, `$(...)` and backticks are not parsed. A Codex `function_call` whose argument list starts with a shell is judged by the element after `-c`, `-lc`, `-Command` or `/c`; any other list is joined with spaces.
- A command's verb class is its first word, lower-cased and without a path or `.exe`, after skipping `VAR=value` assignments, leading segments that are only assignments or `cd <dir>`, and the prefixes `rtk`, `rtk bypass`, `rtk proxy`, `rtk test`, `rtk err`, `sudo` and `time` with their options. A command that is only assignments, including a PowerShell assignment such as `$x = 1` or `$env:KEY='v'`, gives `(assignment)`: an assigned value is never read as a command. For `ssh`, the class is `ssh <remote verb>`; the host is not printed, since a misparse can put a value in its place. A first word that is not a program name (ASCII letters, digits, `.`, `_`, `+` and `-`), such as a variable or a URL, gives `(other)`. The word must also name a program on this machine: a shell builtin, alias or common command from a fixed list, a common PowerShell cmdlet from a fixed list, a program on `PATH` (only absolute folders are searched; on Windows a file with no extension or one in `PATHEXT`, elsewhere a file with an execute bit), or, for a word with a folder in it, an existing file with a program or script extension. Otherwise the class is `(other)`. A word that starts like a network share or a Windows device path (2 slashes or backslashes, or one followed by `?`) is never looked up on disk, because the lookup would contact the host it names; only its file name is checked against the lists and `PATH`. A path that only the system maps to a network location is looked up like a local path: a drive letter mapped to a share, a link to one, an automounted folder such as `/net/<host>` or a relative path when the current folder is on a share. Parsing is heuristic, and this check keeps a value that lands in a program's place, such as an item of a multi-line array or a quoted literal piped to a command, out of the output.
- A test run is a simple command that starts with a test runner (`cargo test`, `cargo nextest run`, `pytest`, `vitest`, `jest`, `node --test`, `npm test`, `npm run test`, `go test` or `dotnet test`, optionally behind `npx`, `bunx`, `uv run`, `poetry run`, `python -m`, `python3 -m` or `py -m`), possibly after the wrappers `agent-heavy`, `nice`, `timeout`, `env`, `nohup`, `time`, `sudo`, `rtk test`, `rtk err`, `do` or `then` with their options and numeric arguments. A runner named in other text, such as `echo cargo test`, is not a test run. It is piped when a single `|` sends it straight into `tail` or `head`. An `ssh` command whose remote command is a piped test run counts as over `ssh`; one piped locally into `tail` or `head` is judged as local.
- A read is `Read`, or a `cat`, `head`, `tail`, `sed` (not `sed -i`), `less`, `more`, `bat`, `Get-Content` or `gc` command, or a `readFile` call in Codex code, found by pattern, so a call inside a string that never runs also counts; `$text = Get-Content x.md` reads `x.md`. Option values, such as `bat -l rust` or a heredoc delimiter, are not paths. Arguments holding `$` or starting with `(`, `@` or `{` are variables or expressions, not paths, and are skipped. Paths are compared lower-cased with forward slashes.
- A hook's label is the file name of its script or, when there is no script, its program; arguments never print. The script is the program itself or the first script argument of an interpreter (`node`, `bun`, `deno`, `python`, `python3`, `py`, `uv`, `bash`, `sh`, `zsh`, `pwsh`, `powershell` or `cmd`) before an option with which that interpreter runs inline code: `-e`, `-p`, `--eval` or `--print` for `node`, `bun` and `deno`; `-c` or `-m` for Python and `-c` for `bash`, `sh` and `zsh`, also at the end of a group such as `-lc`; and `-c`, `-Command`, `-ec` or `-EncodedCommand` in any case for PowerShell. It must be an existing file with a script or program extension, and the program must pass the verb-class check above; otherwise the label is `(other)`. A script on a share-style path is not looked up, as above, so its label is `(other)` unless its file name alone names a program. The name must be plain (ASCII letters, digits, `.`, `_`, `+` and `-`). `VAR=value` and PowerShell assignments and a leading `cd` are skipped first. Recent Claude Code versions record `command hook N` (the hook's position under its event and matcher) or the hook's status message in place of the command; `command hook N` is kept whole, and a status message whose first word is not a program gives `(other)`. Hook rows are keyed by the transcript's `hookName`, which joins the event and matcher, such as `PreToolUse:Bash`, or by `hookEvent` when that is missing; a hook with neither is `(unknown)`. A fractional `durationMs` is rounded.
- A skill is listed in a session when a `skill_listing` attachment in the window names it in its `names`. Its listing characters are its line in the attachment's `content` (`- name`, or a line starting `- name:`, taking the longest such name when one starts another) and the lines after it up to the next such line, each with a newline, the largest in any listing of the session; a listing without `names` lists none. A skill is used when a `Skill` call in the window names it in its `skill` input, or a user message in the window that is text holds `<command-name>/name</command-name>`, as Claude Code writes a slash command; a tool result quoting that text is not read. A skill used but never listed gets no row, and names that print as `(other)` count as one skill of the session. Idle skill characters are priced as idle schema characters are.
- A re-read is a read, after a compaction, of a file read before it and not yet read since. Reread share divides re-reads by every read in the window for that agent and scope, in compacted sessions or not. Reread characters are the size of the result of each Claude call that made a re-read counted in the window. A call that re-reads 2 files is counted once. A result holds what the tool returned, which can be more or less than the file: `Read` numbers each line and can return part of a file, and a shell command prints whatever it prints.
- A command is compared with its earlier runs without leading or trailing white space. A blank command counts among a session's commands but is never a poll or a rerun.
- A poll after a failure is a poll of a command whose previous run in the session, in the window or not, had a result read before the poll was issued with `is_error` set (Claude) or a non-zero `exit_code` (Codex). Only that run's result counts: whilst it is awaited, or if it never comes, the poll does not follow a failure, whatever earlier runs returned, and a result read after a later run of the command was issued is not used. So neither of 2 identical commands issued together, as parallel Claude calls or in one Codex cell, follows the other's failure. Claude Code sets it for a command that exits with an error status and for a call that a hook denied, so a denied call counts although it never ran. Poll characters are the size of the results of the polls counted in the window. The command results table counts every non-blank command in the window by verb class, polled or not, and adds the size of each result read for it, measured as poll characters are; a command whose result is not read counts as a command only. A run whose result is not in the transcript adds nothing to either measure, and a failed run followed by an edit and the same command is a rerun, not a poll. A Codex run whose result is never read (one from a `function_call`, or from an `exec` call without a call id, whose id another call also carries, or whose output never comes or does not pair) leaves the command's last result unknown, so the next poll of it is not counted as after a failure. So does a Claude run whose `tool_use` id another block in the session also carries.
- `tools` counts each call in the window under its tool name, and each result that pairs with it under the same name; an error is a result with `is_error` set, which a hook's denial also is. Image and document blocks in a result are counted, not sized, as their tokens depend on pixels and pages, which the transcript does not record. Web search and fetch rows measure what their results added to context, not what could have been avoided. A cascade is a run of 3 or more erroring results in a row within a session, in the order the results arrive; it is counted once, with its results, when a result that is not an error or the session's end closes it. Retry churn counts each erroring result of a call whose tool and exact input (compared as compact JSON) had erred at least twice before in the session with no success between, so the third such error is the first counted. A call can count in both. Results outside the window count nowhere and neither extend nor end a run. The threshold of 3 follows a comparable tool. A tool name prints only when it is 1 to 128 ASCII letters, digits, `_`, `-`, `.` or `:`; any other name prints as `(other)`.
- `cache` reads each Claude reply that is not synthetic, once per `message.id` (Claude Code writes a record for each block of a reply, each with its usage), into one record (`Reply` in `src/detectors/cache.rs`) whose fields are all required: `message` (an object) with `id` and `model` (strings) and `usage` (an object) holding `cache_creation_input_tokens` (writes), `cache_read_input_tokens` (reads) and `cache_creation` (an object) holding `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`, each count an integer from 0 to 2^40 (more than any context holds, so token sums stay exact); and `timestamp`, a time that parses. A reply with any of these missing, null or of another type is skipped, but for `cache_creation`: an API response may omit it (no source read on 17 November 2026 names the Claude Code versions or platforms that do; this PC's transcripts, from 2.1.260 on, all record it), so a usage without the key reads with no split, counts in `replies_without_split`, and its writes are priced at the 5-minute rate, the lower, and never set the 1-hour lifetime; one without a string `message.id` cannot be matched to its other records, so each of its records counts as a skipped reply. A session's first reply writes `first reply`, unless a `compact_boundary` or a skipped reply came before it. For each later reply, rebuilt tokens are the previous reply's reads and writes less this reply's reads, at least 0 and at most its writes: an estimate of what was cached again, which assumes each reply extends the previous one's prompt. The rest of its writes are `new context`, as are all writes of the first reply after a `compact_boundary` or after a reply skipped in every record of its `message.id`. A rebuild follows an idle gap when the 2 replies' record times are further apart than the cache's lifetime (1 hour once a reply of the session has written any 1-hour tokens, otherwise 5 minutes), else a model switch when `message.model` changed, else it is rebuilt otherwise, as after a rewind. Copies of an earlier session's replies, and replies outside the window, build this state but count nowhere. Dollars are each reply's write tokens times its model's uncached input price (or the `--usd-per-mtok` rate) times 1.25 for 5-minute and 2 for 1-hour tokens, in the proportion the reply records, 1.25 when it records 0 at both lifetimes (Anthropic's prompt caching prices), summed per row and rounded to cents; they estimate what the writes cost, not what could have been saved. `idle_rebuild_share` divides tokens rebuilt after an idle gap by all write tokens. `replies_skipped` counts the replies in the window skipped in every record of their `message.id`, and each skipped record without one; their writes add to no total, so with any skipped the totals are a floor.
- `context` rebuilds each `api-request` record in the window. Its input is its shape's system prompt (the `text` of `shape.system`) and loaded tools (as `schemas` reads them; tools named `mcp__<server>__*` are MCP tools, by server), then its messages: the first `keep` messages of the request its `base` names (all of them when `keep` is larger), then those its `tail` names. Each tail entry is the SHA-256 of a message `{role, content}` as compact JSON with sorted keys, as Claude Code 2.1.325 writes it. A message is found as an `api-request-blob` with that `hash`; a `user` record's message, as written or with text content as one text block; a run of up to 16 consecutive `user` records with no reply between them, which Claude Code 2.1.325 was seen to send as one message holding their blocks (observed in its request logs on 19 November 2026, not a documented format); or a reply: the blocks of consecutive `assistant` records with one `message.id`, in order. A message's text blocks count their text's characters: as system messages when its role is `system`, as reminders when it is a user's and starts `<system-reminder>` after white space, else as text. Other blocks count their compact JSON, as tool results (`tool_result`), tool calls (`tool_use`) or other blocks (such as images), but thinking blocks count their `thinking` text and redacted ones their `data`; any block of a `system` message counts as system messages. A request whose base request or shape its transcript does not hold, whose `base` is neither absent, null nor a string, whose `keep` is not a whole number, or whose `tail` is not a list of 64-digit hexadecimal strings, is not rebuilt (`requests_not_rebuilt`). A request with a message, its own or its base's, that matches nothing in its transcript is partly rebuilt (`requests_partly_rebuilt`); like a request not rebuilt, it counts in no table, and each such message counts in `messages_not_found` once a transcript. A request's input tokens are the uncached, cache write and cache read tokens of the first reply whose `requestRef` names its `id`; `est_input_tokens` gives each part those tokens times its share of the request's characters, by largest remainder (each share rounded down, the tokens left going to the largest remainders, the earlier part on a tie), so a request's parts add up to its tokens; the MCP tools' tokens are split across servers the same way; both are summed over requests. Medians by part count a request without the part as 0; by MCP server they are over the requests that loaded its tools. Times are the request's own `timestamp`, in UTC. The largest requests table lists the requests with tokens, most tokens first.
- `models` reads each Claude reply in the window that is not synthetic, once per `message.id`, into one record (`Reply` in `src/detectors/models.rs`) through the same reader as `cache`: `message` with `id`, `model` and `usage`, whose `input_tokens` and `output_tokens` it reads beside `cache`'s counts and split, and `sessionId`, all required, and `effort` and `attributionAgent`, which a reply may lack. A reply with a required field missing, or any of these null or of another type, is counted in `replies_skipped` (once, when the next reply or the session's end shows no later record of it read) and nowhere else, so with any skipped the totals are a floor; a reply without the `cache_creation` split counts in `replies_without_split`, its writes at 1.25 times. As a skipped reply's model is unknown, a subagent session with one skipped in the window, or whose parent session has one (by the skipped record's `sessionId`, or, when it has none or its blocks name different sessions, every session its file's records in the window name; when no record of the file names one, it marks no session and counts only in `replies_skipped`), ranks as indeterminate, and a subagent session whose every reply in the window is skipped still counts as one. Its key is the scope, `message.model`, the reply's `effort` and its `attributionAgent` (the subagent type), each printed as `(other)` unless it is letters, digits and `_`, `-`, `.` or `:`, and as `(none)` when missing. `input_usd_est` is uncached input at the model's input price, cache writes at 1.25 or 2 times it (as `cache` weighs them) and cache reads at 0.025 times it for Fable and Mythos 5.2 and 5.1, 0.05 for Opus and Sonnet 5.5 and 0.1 for any other model (Anthropic's pricing page, read 16 November 2026), summed per row and rounded to cents; `--usd-per-mtok` replaces the input price, not the multipliers. Output is not priced. `input_usd_share` divides a row's dollars by all rows' before `--limit`. A subagent session's parent is the main session whose `sessionId` its records carry. Models are ranked at their base input price, the price for the shortest prompt, so that a model priced by prompt size (Claude Haiku 5.5, or any tier in a `--prices` file) ranks the same whatever the prompt: a subagent session is on its parent's top-priced model when the cheapest model of its replies in the window costs at least the dearest of its parent's, so the same model on both sides is on top, below when cheaper, and indeterminate when the parent was not read or had no reply in the window, or it or the subagent had a reply in the window on a model without a price; the comparison uses the bundled or `--prices` prices, never `--usd-per-mtok`, and dollars still use each reply's tier. `replies_unpriced` and `unpriced_input_tokens` count the replies without a price (a model without one, or a tiered model whose prompt size is not recorded) and their input, cache write and cache read tokens, which dollars and shares leave out, whatever `--limit` cuts; with `--usd-per-mtok` both are 0.

## Privacy

Fixtures in this repository are synthetic. Tests check, ignoring case, that no sentinel string reaches the output: those in the main fixtures' message text, tool inputs, tool outputs and hook commands, those in the tool outputs of a result-pairing fixture, a Codex results fixture, a Codex record-shapes fixture and a fixture of Codex results printed inside lists and objects, those in the replies and attachments of a startup tokens fixture, those in the replies, attachments and instruction file of a fixture whose replies are all synthetic, those in the skill descriptions, prompts and arguments of a skills fixture, and those in a probe fixture with one on each path found so far by which input text could reach a verb class, hook label or path (PowerShell assignments, hashtables and here-strings, multi-line arrays, comments, heredocs, escaped quotes, `ssh` hosts, URLs, quoted first words, `sudo` and `time` options, reader option values, hook commands, Codex argument lists, `readFile` calls and patch bodies). The probe test also checks that its records reach the detectors. The tests create stub programs and put them first on `PATH`, and their hook commands name stub scripts in `tests/fixtures/hooks`, so their labels do not depend on the machine.

## Interface

`--sample` reads the synthetic transcripts in `src/sample.rs`, compiled in from the test fixtures (the main Claude, Codex and pi ones and the request-log one), each agent's as one root shown as `(bundled sample)`, in the order a folder's files are read. `--json`'s `schema_version` 2 added the dollar and unpriced columns.

## Codex results

Codex writes a `CommandExecution` item in an `event_msg` `item_completed` record as each command ends, with its arguments, exit code, output and start time, but no call id. A command ties to an item when all of these hold:

- The item's command reads as the command's text: the script after a shell flag, as for a `function_call` argument list, trimmed, with `rtk ` dropped where a simple command starts in both texts, as the RTK hook adds it to the commands it filters.
- The item ends whilst the command's call is open, and its command started no earlier than the call was recorded, so a command an earlier call left running cannot tie. A call whose record has no time takes no item.
- No other command could have run it: none of another open call that has no recorded time or was recorded before the item's command started, of a call without an id, which stays open for the session as its output cannot be found, or untied in a call whose output came whilst one of those calls was open, as such a command may still be running, has that text.
- The call has no other command with that text and no other such item. A text the call runs more than once ties to none, as code need not run commands in the order it writes them.

`bigsister` does not follow values through a cell's code to find a command's text or result: that needs a JavaScript interpreter, and it would still guess wherever a value depends on what ran. A command whose text the cell builds from values does not tie.

A tied command takes the item's exit code and output: `pipes` judges that output, which is what the command wrote, as a Claude Bash result is. `polls` counts as poll characters only what the cell printed of it, which is what reached the model: the cell's one printed result when it has one command, otherwise a printed result with the item's exit code and an output that is the item's or ends it, as `exec_command` keeps the end of a long output, and that shows no other tied command's item. A printed result that could be more than one command's counts for none. In a cell with a command no item ties, which could own any printed result, a tied command counts only the result printed whole in its own place, and only when the untied command pairs by position.

A command no item ties pairs with the result printed at its position when the cell printed one result per command and has one command, or Codex recorded no item whilst the call was open, as older Codex versions record none, or it is the one command left untied, every tied command's result is printed whole in its own place and the result in its place shows no tied command's item.

On one machine's rollouts (1,056 files, a snapshot taken on 14 November 2026), `shaphan polls --agent codex` (`bigsister`'s name before 0.2.0) before and after this pairing: calls not paired fell from 24,228 to 7,752, commands not paired from 32,890 to 9,327 of 101,192, and polls after a failure rose from 35 to 49. Poll characters fell from 817,075 to 613,883, mostly as polls of commands that their cells built from values, which were paired by position, now pair with nothing. Before it, printed results were paired by position, and the items showed 5 of 4,767 results in cells of several commands credited to another command, in cells that printed each result as it came.

`pipes` counts cells, not commands, under `codex_outputs_not_paired`. The unguarded test runs whose results were not judged are `unguarded` minus `unguarded_results_found`, for either agent, so a count of commands would repeat it.
